## 1. Purpose

Athena accepts a natural-language learning goal and returns a structured curriculum assembled from sources it discovers, ranks, and organizes at runtime. It queries external platforms, scores candidates with a multi-dimensional heuristic, refines the ranking through a consensus mechanism, indexes the results into a local vector store for subsequent retrieval, and produces a learning path that respects a stated difficulty level. Every stage operates under a hard token budget and absorbs external failures without aborting the run.

## 2. Layered Architecture

The system is divided into two layers that execute in the same process but remain logically independent.

The lower layer is a deterministic pipeline. It performs query expansion, concurrent fetching across heterogeneous platforms, normalization, deduplication, validation, heuristic scoring, consensus ranking, source summarization, learning path construction, path enhancement, and multi-format persistence. Each stage is a self-contained module that can be tested and reasoned about in isolation.

The upper layer is an autonomous controller. It plans the run, allocates a token budget across categories, iterates a Think–Act–Observe–Reflect loop, selects tools from a runtime registry, maintains short-term, long-term, and episodic memory, and reflects on the quality of intermediate results. The controller never bypasses the pipeline; it invokes pipeline stages as tools and reacts to their outputs.

The division is deliberate. The pipeline stays predictable and independently testable. The controller absorbs the uncertainty of live external services.

## 3. Retrieval

Retrieval begins with a query understanding stage that corrects the topic, extracts a primary concept, generates keywords, classifies intent, detects learner level, and assigns target subject domains. The correction stage strips filler phrases — polite requests, imperative verbs, compound colloquialisms such as *life of X*, *world of X*, *story of X* — so that the concept string passed downstream contains only content-bearing terms.

Subject-domain detection compares the query against a vocabulary of aliases maintained in the domain registry. Education and general are treated as intent modifiers, not as subjects. When no subject domain fires, the router falls through to a diverse universal platform pool that spans reference material, textbooks, research indexes, and code repositories. When a subject domain fires, its platform list is used and the intent modifier adjusts ranking rather than platform selection.

Fetching runs concurrently across the selected platforms under a semaphore. Each client inherits a common base that provides connection pooling, per-platform token-bucket rate limiting, retries with exponential backoff and jitter, response caching, and uniform error translation. A hung platform cannot consume the whole tool budget; the orchestrator is bounded at fifty-five seconds and the tool at seventy-five, with a direct fallback path if the orchestrator fails.

Normalization maps every retrieved item into a single schema with a deterministic identifier derived from platform, URL fingerprint, and title. Deduplication runs in three passes: exact match on DOI or arXiv identifier, URL fingerprint after stripping tracking parameters, and fuzzy title matching by Levenshtein distance. When two records describe the same work, the richer record survives and absorbs the metadata of the other.

## 4. Scoring and Consensus Ranking

Before any language model is consulted, each source receives a composite score over eight weighted dimensions: fuzzy token overlap with the query, platform authority, source-type quality, log-saturated citation impact, recency, content completeness, PDF or code availability, and author completeness. A learner-alignment multiplier reduces the score of an advanced source offered against a beginner request, and of an introductory source offered against an advanced request. This heuristic is the floor beneath which the system cannot fall. It is the reason a run still produces a ranked list when every language-model provider is offline.

Consensus ranking dispatches the highest-scoring candidates concurrently to three independent providers. Each ranking is fingerprinted by hashing its ordered identifier list. Agreement is the fraction of votes sharing the most common fingerprint. If agreement reaches the configured threshold, the majority ranking is accepted. Otherwise a judge model reads all votes and their reasoning and selects one. If every provider fails, the heuristic order is returned unchanged.

Two gates operate before the language model is invoked. A relevance gate retains sources whose overlap with the concept exceeds a proportional floor. A topic-presence gate retains sources whose tokens share any meaningful match with the query's concept tokens. Both gates include a rescue path: if the gate would leave fewer than the minimum working set, the highest-scoring dropped sources are returned to the pool. The gates exist to keep off-topic material out of the model's context, not to starve the model of candidates.

The output of consensus ranking is a ranked list whose top entries are then summarized, embedded, and used to construct a learning path.

## 5. RAG Subsystem

The vector store is a SQLite database with two schemas: a parent-document table and a chunk table, both indexed by FTS5 for keyword retrieval and by packed floating-point blobs for semantic retrieval. A document is written as one parent row plus zero or more chunk rows depending on its length. Chunk size and maximum chunks per source are read from configuration. Documents shorter than the configured chunk size produce a single chunk identical to the parent.

Embedding is performed through a single provider with batching, retry, and backoff. Every parent and every chunk receives a vector. The store records per-document and per-chunk embedding coverage so the doctor command can report completeness.

Chat retrieval has three operations. Keyword search runs an FTS5 match and normalizes the BM25 rank into a bounded score. Embedding search scans stored vectors and computes cosine similarity. Hybrid search combines both by a weighted sum. A wrapper named `hybrid_search_v2` decides which operation to invoke based on the number of content-bearing tokens in the query.

The gate that decides between chunk and parent search was originally a hardcoded value. It is now read from configuration and adjusted by an adaptive step: if the query contains an interrogative or comparison marker, the effective gate drops by one, never below a configured floor. The decision, the token count, the effective threshold, and the source of that threshold are all recorded in the retrieval diagnostics so that `--explain` can report them.

Chunk retrieval returns parent documents whose highest-scoring chunk carries the query's content. The matched chunk is written into the parent's metadata and read downstream by the passage builder so the language model receives the relevant passage, not the parent's opening lines.

Confidence scoring blends retrieval score, title overlap, platform coherence, citation coverage, answer length relative to the requested style, and citation diversity. Two corrections run after the blend. A refusal detector caps confidence when the language model declares insufficient context, and a weak-topic detector caps confidence when title overlap with the query falls below a threshold. Both corrections append a step to the fallback ladder so the diagnostic record shows why the cap was applied.

## 6. Catalog Mode

The system distinguishes between three kinds of questions. Corpus questions ask about a topic inside the indexed documents. Conversation questions ask about the session history. Catalog questions ask about the corpus itself — what it contains, how many sources, what platforms, what topics, what dates.

Catalog detection is performed by a weighted multi-signal classifier. Six independent signals are scored: presence of corpus-possession vocabulary, presence of meta-content vocabulary, presence of second-person reference, presence of an interrogative shape, weakness of topic extraction, and presence of a structural comparison. Each signal carries a configurable weight. The signals are summed, normalized against the total possible weight, and compared against a configurable threshold. No single phrase decides the route. A high score requires that multiple independent signals agree.

When the catalog route fires, retrieval is bypassed entirely. The catalog handler reads a snapshot from the vector store: total document count, breakdown by platform, breakdown by source type, breakdown by run, date range, and the most recent titles. The snapshot is passed to a language model under a catalog-specific prompt that instructs it to describe the corpus using only the snapshot data and never to retrieve or invent sources. The answer reports the same diagnostics as a normal chat answer — route, score, signals fired, snapshot contents — so `--explain` is a complete audit.

Catalog mode closes the failure mode in which a meta-question about the corpus was routed through topical retrieval, produced nonsense expansion queries, and returned a refusal.

## 7. Autonomous Loop

The controller decomposes the goal into subtasks, allocates budget, and iterates. Each iteration begins with a planning phase that selects the next action. It executes the chosen tool. It parses the tool's output and updates state. It scores the quality of the result against the goal and maps the score to a decision by a fixed matrix: accept and advance, apply a minor fix, retry with a different approach, or restart the subtask.

Tool invocation goes through an executor that validates parameters, checks the token ledger before executing, applies a per-tool timeout, and records the outcome in the event stream. Tool failure is an ordinary observed outcome, not an exception that ends the run.

The loop tracks consecutive iterations that produce no new sources. When the streak reaches a configured limit, the loop terminates with a clear failure reason rather than continuing to consume budget on empty searches.

## 8. Token Ledger

Every run receives a hard allowance, subdivided into category ledgers for planning, search, reading, ranking, summarization, reflection, and synthesis. Every provider call reports its token usage through a hook that is registered on the shared manager. The hook registry is held at the class level so that every manager instance — shared, borrowed, or freshly created — reads the same list. This corrects an earlier failure in which hooks registered on the shared manager were invisible to the fresh manager that made the actual calls, and the ledger reported zero for a two-minute run.

The ledger tracks total consumption, remaining budget, per-category consumption, and a circuit breaker that trips when consumption crosses warning and critical thresholds. When the remaining budget crosses the wrap-up threshold, the controller stops exploring and synthesizes immediately from accumulated material. The wrap-up mode is what keeps the run within the free-tier allowance even when the earlier stages have consumed more than expected.

## 9. Model Routing and Multi-Key Rotation

Model selection is driven by the routing rules in configuration and by a router that maps each task to a chain of model references. Fast tasks — query expansion, query intelligence, summarization, reflection, tool selection — use the fast chain. Strong tasks — consensus ranking, learning path construction, path enhancement — use the strong chain. Judge tasks use the judge chain. Code tasks use the code chain.

The router detects the provider from the model name using a keyword heuristic. When a name carries an explicit provider prefix — `groq:`, `sambanova:`, `mistral:`, `google:`, `nvidia:` — the prefix overrides the heuristic. This removes ambiguity for model identifiers that exist on multiple providers.

Provider keys support multiple credentials per provider. The primary variable accepts a comma-separated list, and additional variables with the `_2`, `_3` suffixes are read the same way. The provider layer orders the keys by cooldown state, attempts a call against the first available key, and on a rate-limit or balance response marks that key as cooling for a configurable duration and retries the call against the next key. When every key is cooling, the call surfaces the rate-limit error. This is what turns two or three accounts on the same provider into an effective multiplier on the rate limit without code changes.

The routing table itself is config-driven. Adding a new model to a chain, moving a model between tiers, or retiring a dead endpoint is a configuration edit, not a code change.

## 10. Learning Path and Enhancement

The learning path builder takes the ranked source list and the query schema and produces an ordered sequence of steps. Each step has a title, an objective, an estimated duration, and a set of resources drawn from the ranked list. The builder consults the difficulty classifier to align step difficulty with the target learner level.

The path enhancer adds prerequisites, projects, and key concepts to each step. It runs in two modes. If a language model is available, the enhancer sends a structured prompt containing the ordered steps, the topic, and the level, and asks for step-level enrichment. If the model is unavailable or its output fails validation, a heuristic enhancer produces generic enrichment from step titles and resource metadata.

The enhancer treats the incoming step order as authoritative. It does not re-order steps by their average resource difficulty, because the builder already produced a pedagogically ordered sequence. It aligns resource ordering within a step, updates the objective annotation, and leaves the step order unchanged. The prompt explicitly forbids listing other steps in the path as prerequisites. This correction eliminates the failure mode in which step one listed completion of steps two and three as prerequisites.

## 11. Resilience

The governing rule is that no single external failure may abort a run. Rate limits are handled by backoff against the same key and by rotation to the next key. Timeouts are bounded at the tool level, and the retrieval layer has a direct fallback if the orchestrator itself fails. Deprecated model endpoints are removed from the routing tables by configuration. Total rejection of model rankings triggers the heuristic scorer as a fallback. Budget exhaustion triggers wrap-up mode. Every degradation is logged as an event with the reason and the action taken, and the final report reproduces the degradation ladder in its diagnostics panel.

## 12. Persistence

Every run produces four artifacts: a JSON payload with the full result, a Markdown report with the same content in human-readable form, an HTML report styled for reading, and a row in the SQLite store keyed by request identifier. Ranked sources, summaries, the learning path, the enrichment, warnings, and the token report are all preserved. The store is shared across runs so that the retrieval layer can query historical material and the catalog handler can describe the corpus as a whole.

## 13. Current State

The retrieval layer now queries diverse platforms for beginner queries instead of restricting to textbooks. The domain router distinguishes intent from subject. The chunk gate is config-driven and adaptive. Chunk retrieval reaches the language model with the actual matched passage. Refusals are detected and reported honestly. The catalog route handles corpus questions without retrieval. The autonomous loop aborts on persistent empty searches instead of consuming the budget on them. The token ledger reports real consumption. The routing table points only at models confirmed working on the configured accounts. Multi-key rotation is active on every provider that exposes multiple credentials.

Remaining known limitations are documented and isolated. The learning-path enhancer can still place borderline sources into steps when the retrieved pool is thin. Cross-disciplinary queries whose concept tokens do not overlap any returned title are rescued by a minimum-three fallback and then judged by the model. The live interface counter does not always sync with the iteration number shown in the header; this is cosmetic and does not affect execution. These are tracked as independent items, not as regressions.
